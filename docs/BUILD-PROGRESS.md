# Build Progress

**Status definitions**

- **Done** — the FR's core described capability is functionally implemented (even against mock/local data with no real backend), including its primary user actions.
- **In Progress** — some real UI/logic exists addressing part of the FR (e.g. a read-only view of the data it describes), but its core action(s) are not implemented yet.
- **Not Started** — no code in the repository addresses this FR.

**Access-control note (2026-10-03):** the API routes now enforce roles server-side. Sign In returns a signed session token (`lib/auth/server-session.ts`; sliding 7-day expiry; HMAC with `SESSION_SECRET`, or a key derived from `DATABASE_URL` when unset); every route re-reads the account per request (so role changes and deactivation apply immediately) and checks the role against PRD 9 plus what the UI actually calls the route for (`lib/auth/api-roles.ts`). Adopters and Council Officers get only their own records (applications, agreements, payments, Meet and Greets, follow-up visits, checks, adopter profile, council transfers, notification read state) and only public animal fields/photos (PRD 9.1); writes to those records must be their own (an Adopter may only edit a Draft application). Field-level rules: each side of the Review Adoption Fitness joint confirmation can only be recorded by its own role, in its own name; a Veterinarian may only make the lazy hold-expiry update on a statutory hold. Notifications compute only the signed-in role's notification types. Sessions are per tab: the token is kept in that tab's sessionStorage (`lib/auth/client-session.ts`) and sent as `Authorization: Bearer` on every API request through `lib/shared/http.ts` - not a cookie, which the whole browser profile would share - so several tabs/windows can be signed in as different roles at once, refreshing a tab keeps its user, closing it ends its session, a newly opened tab starts signed out, and signing in, out or renewing in one tab never affects another. The session is sliding: 7 days from the last API activity, with the tab renewing its token through `/api/auth/session` at most hourly. On every page load the tab restores from `/api/auth/session` (full user, plus a renewed token when due); only an explicit 401 (no valid session, or the account is now Inactive/Locked) signs it out - a server error, network failure or timeout keeps the stored user - and any later API 401 also signs it out. Photo images are served from signed, expiring URLs handed out in the role-checked photo lists, since an `<img>` cannot send the header. Known gaps: actor names inside request bodies (e.g. audit `userName`, `completedByName`) are still client-supplied, and where one role legitimately triggers another domain's write (e.g. a Veterinarian's medical action completing an Adoption Fitness task) that route admits the role for the whole route, not per field.

**Process engine note (2026-10-06):** `lib/process/engine.ts` computes each animal's journey (Intake; Microchip; Implant/Vaccination/Desexing; Health & Medical Clearance; Behaviour; Fitness Review; Publish; Application; Documents; Suitability Checks; Meet and Greet; Agreement; Payment; Payment Confirmation; Pre-Release Check; Release; Follow-Up; Rehomed) purely from existing records - no process table. Each step has a state (not started / waiting / in progress / done / blocked), the role(s) responsible and the role(s) that must act now; Administrator acts wherever Shelter Staff does. Steps an animal's own status shows it has already passed count as done even without records (the seeded sample animals). `lib/process/load.ts` reads every table once, in parallel (photos as metadata only), and groups by animal. Served by `GET /api/process/animals/:id` (tracker; Administrator, Staff, Vet), `GET /api/process/applications/:id` (application journey; care team or the owning Adopter), `GET /api/process/transfers` (a Council Officer's own transfers, status only) and `GET /api/worklist` - one batch per tab with "needs my action" items, list flags/ordering, sidebar badge counts and payments awaiting confirmation. A shared animal layout (`app/animals/[animalId]/layout.tsx`) puts the tracker, with a five-colour legend, keyboard-accessible role tooltips and a red dot for the viewer's own steps, on every animal page; Animals and application lists sort needs-my-action items first (before pagination); the Staff/Admin home shows "Needs my action"; Adopters get an application journey and Council Officers a transfer status view. The worklist refreshes every 20 s, on window focus and right after any write; its first load waits until the page's own data has loaded (except where it is the page's main content), and the tracker loads when the browser is idle, so neither slows page loads. The database client uses an explicit 25-connection pg pool (Neon's pooled endpoint) so these parallel reads go out in one wave.

**Microchip implant and fitness note (2026-10-06):** When Scan Microchip finds no chip, `POST /api/microchip-implants` (Staff/Admin) assigns a new, globally unique 15-digit number with the prefix 036 (checked against animals, scan records and other implant tasks) and creates a Veterinarian implant task (`MicrochipImplantTask` model), audited in the same transaction; a second No Chip scan returns the same pending task. The Vet sees these under the new "Microchip Implants" nav item (badge from the worklist) and records one implant session at `/animals/:id/microchip-implant`: implant confirmation, a vaccination and a desexing schedule or exemption. Vaccination and desexing are saved first, then `POST /api/microchip-implants/:id/complete` (Veterinarian only) completes the task, sets the animal's microchip number and marks the Microchip Check task Continuable in one transaction. An Owner Match still starts the Statutory Hold as before. Issuing a Medical Clearance (`POST /api/medical/clearances`, Veterinarian only, issuer taken from the session) now also records the Veterinarian half of Review Adoption Fitness in the same transaction, with the note "Confirmed together with Medical Clearance", and both are audited. A new unresolved Statutory Hold withdraws that confirmation in the hold's transaction (audited); the clearance can then be issued again to re-confirm. Pre-Listing has no way back to Not Fit, so an animal already in Pre-Listing stays there, but Publish is blocked until both halves are confirmed again. There is no separate clearance revoke flow. `POST /api/fitness-reviews` is now Staff/Administrator only and records just the Staff half; the stored Vet half is always kept as is, so an Administrator cannot set it. Review Adoption Fitness and Publish are one Staff page: the Vet half reads "Confirmed with Medical Clearance" or "Waiting on Veterinarian: Medical Clearance", and once the animal is Pre-Listing the page shows Publish. Leaving it unpublished shows a reminder, and Publish stays in Needs my action. The page's Pre-Listing and Publish blockers come from `GET /api/process/animals/:id`, which works them out on the server from the records it already loads, and assessment tasks are fetched per animal, so the page loads 20 KB instead of 93 KB. Photo alt text is optional everywhere and no longer blocks Publish. Vaccination and desexing records are now audited.

**Application documents and payment note (2026-10-06):** Adoption application documents are now stored in the database: the `StoredFile` table holds the metadata and `StoredFileChunk` holds the content as base64 chunks of at most 2 MB, so no request or response exceeds the hosting body-size limit. The Adopter uploads them (only to their own Draft application) through `/api/files`. Uploads are limited to PDF, JPG and PNG up to 5 MB, further narrowed by the Rule Configuration's `allowedAttachmentTypes` and `maxAttachmentSizeMB` (`GET /api/files/rules`). The server checks the extension, the declared size, each chunk's exact length and the file's real content (magic bytes), and drops a refused upload. When the last chunk arrives, the file is marked complete, listed on the application and audited ("Upload Application Document") in one transaction; removing one is audited too. The application keeps metadata only and `PATCH /api/applications/:id` no longer accepts `documents`. List endpoints return metadata only. Downloads go through the protected chunk route, assembled in the browser, because the session is a per-tab bearer token, not a cookie. Shelter Staff, Administrators and the owning Adopter can list and download; Veterinarians and Council Officers get 403 and receive applications without their documents. The tracker's Documents step reads "Documents received (n)". Council Transfer attachments are still metadata only, as they are added before the transfer exists, but the form now applies the same type and size rules. The Staff/Administrator home shows "[Adopter] has completed payment for [Animal]. Please confirm." once per payment per tab session; the payment stays in Needs my action until confirmed. The payment screens no longer describe the payment as simulated.

**Vaccination Check note (2026-10-07):** In the Veterinarian's microchip implant session, step 2 is now a Vaccination Check instead of giving a vaccine.

**The check form.** It records:
- a check date (defaults to the local date)
- antibody/titre results, added inline as one or more rows and saved as `AntibodyCheck` records
- optional evidence of vaccinations the animal already had (vaccine type, date given, source; it counts as current for 365 days)
- a required report

**Coverage and pending items.**
- The required vaccine types are the active "Vaccine Type" options tagged with the animal's species, plus untagged ones. Today none are tagged, so the whole list applies.
- A type is covered if every antigen it protects against has a current Protective result, or if a vaccination record or evidence for it is current. "Kennel Cough (Bordetella)" now maps to Bordetella only.
- The rest is listed before saving with all boxes ticked. The Veterinarian can untick items that don't apply, which are recorded as not applicable.
- The outcome reads "Fully covered", "Partially covered – N items pending" or "No vaccination cover – all items pending".

**Saving.** `POST /api/medical/vaccination-checks` (Veterinarian only) recomputes coverage from the stored records and saves, in one transaction:
- the antibody rows
- the `VaccinationCheck` (with evidence, coverage and not-applicable lists as JSON)
- a `VaccinationTask` (Pending) for each kept type not already pending

Each row is audited. The implant session saves the check with the desexing record and the implant, as before.

**The Medical Record page.** The section is now "Vaccination Check and Records". It shows:
- the latest check, with a "Run Vaccination Check" button for animals that don't come through the implant session
- pending items, each with "Record administration" (the vaccination form prefilled and locked to that type) and "Waive" (reason required)
- completed and waived items
- the vaccination records, with ad-hoc "Record Vaccination" kept

Recording against an item (`vaccinationTaskId` on `POST /api/medical/vaccinations`) completes it in the same transaction, and the vaccine type must match. Waiving uses `POST /api/medical/vaccination-tasks/:id/waive` (Veterinarian only). Both are audited. The antibody question still applies, both to ad-hoc vaccinations and to pending items whose antigens are covered.

**Medical Clearance.** It now requires a Vaccination Check, and no item still Pending. Animals from before checks, such as Ruby, pass with a vaccination record. Desexing and recheck rules are unchanged.

**Tracker and Vet Workbench.** The process engine reads the check and pending items in the same batch load (two more parallel queries, no per-animal requests).
- "Implant / Vaccination / Desexing" stays with the Veterinarian until the check is done and nothing is pending.
- "Health & Medical Clearance" waits on the Veterinarian while items are pending.
- The Vet Workbench lists the pending count and types.

New read endpoints: `GET /api/medical/vaccination-checks` and `GET /api/medical/vaccination-tasks` (care team, `?animalId=`). The permission test now runs 435 checks.

**Vaccine model note (2026-10-07):** Vaccine types are now data-driven, so types an Administrator adds work without code changes.

**Admin fields (Vaccine Type options only).** In Admin > Dropdown Options, each Vaccine Type option has two optional fields:
- "Applicable species": checkboxes from the live Species list, stored as Species option ids, so species are compared by stable key and newly added species such as Rabbit appear.
- "Covers (antigens)": comma-separated short names, normalised and de-duplicated.

They are stored as JSON in the new nullable `DropdownOption.applicableSpecies` / `coversAntigens` columns, validated on the server, and shown resolved on the option's view, marked "(built-in default)" where applicable. The helper text reads "Vaccine types without an applicable species are not offered to Veterinarians." Dropdown option create, edit, retire and restore are now audited on the server in the same transaction (they weren't audited before). Changing an option never alters existing vaccination records.

**Resolution** (`lib/medical/vaccine-model.ts`, shared by screens and routes):
- Administrator values win.
- Otherwise the built-in options use a default map keyed by their seeded id (`Vaccine Type:C5` etc.), because some display values have since been edited:
  - C3 = Dog: parvovirus, distemper, hepatitis. C4 = C3 + parainfluenza. C5 = C4 + bordetella. C7 = C5 + leptospirosis strains.
  - Kennel Cough (Bordetella) = Dog: bordetella.
  - F3 = Cat: feline enteritis, herpesvirus, calicivirus. F4 = F3 + FeLV. F5 = F3 + chlamydia + FeLV.
  - Reptile Preventive Health Check = Reptile, covering itself.
- Otherwise an option covers one antigen named after its value and has no species, so it is never offered.
- Older long antigen names (e.g. "Canine parvovirus") map to the short ones, so earlier antibody results still count.

**Vaccination Check.**
- Required antigens = all antigens of the active types for the species.
- Covered antigens = current Protective antibody results, current recorded vaccinations, and evidence rows from the check (365 days).
- Pending items (still one per vaccine type) are proposed by greedy cover of the gap. Among the types lying wholly inside the gap, the one covering most is chosen, ties alphabetical; if none fits, the one with the largest overlap. Proposals are ticked by default, and the Vet can untick them or add other applicable types; unticked ones are recorded as not applicable.
- A species with no configured types shows "No vaccine types are configured for this species. An Administrator can add them under Dropdown Options." The check and report can still be saved, and the implant session completes.

**Multi-vaccine administration.** `POST /api/medical/vaccinations/batch` (Veterinarian only; the single route now uses the same logic) saves several vaccines given together: one shared date, and a dose/batch ID and booster date per vaccine. It is all or nothing:
- Each vaccine completes its pending item, and any other pending item whose antigens are now all covered is completed too (e.g. giving C5 completes Canine Parainfluenza and Kennel Cough).
- Vaccines covering an antigen with a current Protective result need a reason each. Missing any means 409 with every flagged vaccine listed, and the form shows one modal with a reason per vaccine.
- A pending item already completed meanwhile rolls the whole batch back.
- Overlapping antigens between selected vaccines show a non-blocking notice.

The pending list on the Medical Record page and in the implant session has checkboxes and "Record administration for selected".

**Species enforcement.**
- Every vaccine picker (record vaccination, pending items, evidence rows, "add another") lists only the species' types.
- The antibody antigen field is a dropdown of the species' antigens.
- The server rejects with 422 a vaccine, antibody antigen, evidence row or pending item that doesn't apply to the animal's species. Existing records are untouched and still display (Ruby unchanged).

**Species lists.** The species lists on the intake form, the breed option dialogs and the adopter profile now come from the Species options. The permission test (449 checks) covers the batch route and the 422/400 rejection cases.

**Setup and cleanup.** The four dog and cat single-component types were configured through the Admin UI. RHDV2 and Myxomatosis need "Rabbit" set as their applicable species once that species exists; a throwaway test species used for the rabbit checks was removed afterwards.
