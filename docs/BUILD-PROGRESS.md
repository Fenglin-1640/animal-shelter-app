# Build Progress

Tracks implementation status for every functional requirement in `docs/PRD.md` section 6 (FR-AUTH-01 through FR-REL-02). Status reflects the actual code in the repository, not intent or planning.

**Status definitions**

- **Done** — the FR's core described capability is functionally implemented (even against mock/local data with no real backend), including its primary user actions.
- **In Progress** — some real UI/logic exists addressing part of the FR (e.g. a read-only view of the data it describes), but its core action(s) are not implemented yet.
- **Not Started** — no code in the repository addresses this FR.

**How to keep this current**: after finishing a module, update its row's Status and Notes here, and include this file's diff in that module's commit.

**Storage-layer note (2026-09-19):** every "no real backend" / `localStorage` / "client-side" detail in the Notes column below (e.g. FR-AUTH-01, FR-SA-01, FR-ADP-01, FR-MC-02, FR-NOT-01) describes the implementation as of this file's last FR-completion update. A later migration moved every domain-data store off localStorage onto a real Prisma + SQLite backend; that migration is now complete - see `prisma/README.md`'s "Migration status" section for the current source of truth. None of this affects the functional Status below, only the persistence mechanism, so the FR rows themselves haven't been rewritten to match.

**Access-control note (2026-10-03):** the API routes now enforce roles server-side. Sign In returns a signed session token (`lib/auth/server-session.ts`; sliding 7-day expiry; HMAC with `SESSION_SECRET`, or a key derived from `DATABASE_URL` when unset); every route re-reads the account per request (so role changes and deactivation apply immediately) and checks the role against PRD 9 plus what the UI actually calls the route for (`lib/auth/api-roles.ts`). Adopters and Council Officers get only their own records (applications, agreements, payments, Meet and Greets, follow-up visits, checks, adopter profile, council transfers, notification read state) and only public animal fields/photos (PRD 9.1); writes to those records must be their own (an Adopter may only edit a Draft application). Field-level rules: each side of the Review Adoption Fitness joint confirmation can only be recorded by its own role, in its own name; a Veterinarian may only make the lazy hold-expiry update on a statutory hold. Notifications compute only the signed-in role's notification types. Sessions are per tab: the token is kept in that tab's sessionStorage (`lib/auth/client-session.ts`) and sent as `Authorization: Bearer` on every API request through `lib/shared/http.ts` - not a cookie, which the whole browser profile would share - so several tabs/windows can be signed in as different roles at once, refreshing a tab keeps its user, closing it ends its session, a newly opened tab starts signed out, and signing in, out or renewing in one tab never affects another. The session is sliding: 7 days from the last API activity, with the tab renewing its token through `/api/auth/session` at most hourly. On every page load the tab restores from `/api/auth/session` (full user, plus a renewed token when due); only an explicit 401 (no valid session, or the account is now Inactive/Locked) signs it out - a server error, network failure or timeout keeps the stored user - and any later API 401 also signs it out. Photo images are served from signed, expiring URLs handed out in the role-checked photo lists, since an `<img>` cannot send the header. Known gaps: actor names inside request bodies (e.g. audit `userName`, `completedByName`) are still client-supplied, and where one role legitimately triggers another domain's write (e.g. a Veterinarian's medical action completing an Adoption Fitness task) that route admits the role for the whole route, not per field.

**Process engine note (2026-10-06):** `lib/process/engine.ts` computes each animal's journey (Intake; Microchip; Implant/Vaccination/Desexing; Health & Medical Clearance; Behaviour; Fitness Review; Publish; Application; Documents; Suitability Checks; Meet and Greet; Agreement; Payment; Payment Confirmation; Pre-Release Check; Release; Follow-Up; Rehomed) purely from existing records - no process table. Each step has a state (not started / waiting / in progress / done / blocked), the role(s) responsible and the role(s) that must act now; Administrator acts wherever Shelter Staff does. Steps an animal's own status shows it has already passed count as done even without records (the seeded sample animals). `lib/process/load.ts` reads every table once, in parallel (photos as metadata only), and groups by animal. Served by `GET /api/process/animals/:id` (tracker; Administrator, Staff, Vet), `GET /api/process/applications/:id` (application journey; care team or the owning Adopter), `GET /api/process/transfers` (a Council Officer's own transfers, status only) and `GET /api/worklist` - one batch per tab with "needs my action" items, list flags/ordering, sidebar badge counts and payments awaiting confirmation. A shared animal layout (`app/animals/[animalId]/layout.tsx`) puts the tracker, with a five-colour legend, keyboard-accessible role tooltips and a red dot for the viewer's own steps, on every animal page; Animals and application lists sort needs-my-action items first (before pagination); the Staff/Admin home shows "Needs my action"; Adopters get an application journey and Council Officers a transfer status view. The worklist refreshes every 20 s, on window focus and right after any write; its first load waits until the page's own data has loaded (except where it is the page's main content), and the tracker loads when the browser is idle, so neither slows page loads. The database client uses an explicit 25-connection pg pool (Neon's pooled endpoint) so these parallel reads go out in one wave.

**Seed-data note (2026-09-26):** the PRD 12.1 seed animals (`lib/animals/mock-animals.ts`, written by `prisma/seed.ts`) demonstrate specific lifecycle states, not a full history. Luna, Charlie, Daisy, Rocky and Oliver are seeded straight into their states with none of the records a real animal would have passed through to get there (assessment tasks, Review Adoption Fitness sign-off, Medical Clearance, etc.), so they don't satisfy every gate that state implies. Ruby (A-0006, "Vet cleared, waiting for Staff to publish") is the exception: `seedRubyPrerequisites()` seeds her complete Pre-Listing history (3 completed assessment tasks backed by a No Chip lookup, a Health Assessment and a Suitable Temperament Assessment; the Staff + Veterinarian Review Adoption Fitness confirmation; Medical Clearance backed by a vaccination and a species desexing exemption; an adoption fee; and a public photo with alt text), so Staff can actually publish her in the demo.
